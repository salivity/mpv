Reduce Audio Buffer Size in MPV for Live Streams

While mpv does not allow you to define an exact hardware buffer size in raw bytes or sample frames, you can strictly control audio buffer duration and stream caching to minimize latency during live playback. By pairing the --audio-buffer option with mpv's built-in low-latency profile and demuxer tweaks, you can reduce audio delay to a fraction of a second without losing playback stability.

The --audio-buffer Option

The primary setting for controlling audio buffering in mpv is --audio-buffer. This option accepts a duration in seconds rather than a byte count:

mpv --audio-buffer=0.05 <stream-url>

The default value is typically 0.2 seconds (200 milliseconds). Lowering this value to 0.05 (50 milliseconds) or even lower reduces the audio queue stored before it reaches the sound card. Setting this too low may cause audio crackling or underruns if your system cannot process audio chunks fast enough.

Combining with Low-Latency Settings

Changing the audio buffer alone is often insufficient for live streams because mpv’s demuxer and video queues also introduce delay. To achieve the absolute lowest latency, combine --audio-buffer with the following parameters:

mpv --profile=low-latency --audio-buffer=0.02 --untimed <stream-url>
  • --profile=low-latency: Disables internal read-ahead caching, disables frame dropping smoothing, and optimizes demuxing for real-time delivery.
  • --untimed: Skips synchronization clocks so frames and audio packets are decoded and output as fast as they arrive, which is ideal for real-time monitoring.
  • --demuxer-lavf-o=fflags=+nobuffer: Passes flags directly to FFmpeg's libavformat to prevent internal network stream buffering.

Audio Driver Backends

The effectiveness of minimal audio buffer sizes depends heavily on your audio output driver (--ao):

  • Linux (PipeWire/PulseAudio): PulseAudio and PipeWire dynamically adjust latency. You can force lower latency requests using --ao=pulse or --ao=pipewire.
  • Linux (ALSA): Direct hardware access via --ao=alsa often supports the lowest possible buffer times, though it may lock the device exclusively.
  • Windows (WASAPI): Using --ao=wasapi with --wasapi-exclusive=yes bypasses the Windows audio mixer, enabling lower hardware buffer thresholds at the expense of muting other applications.

Potential Trade-offs

Minimizing buffer sizes leaves very little room for network jitter or CPU load spikes. If the audio buffer completely drains before new network packets arrive, you will hear popping, stuttering, or temporary silence. For live network streams (such as RTSP, RTMP, or HLS), maintain a buffer between 0.05 and 0.1 seconds to balance low latency with uninterrupted sound.
